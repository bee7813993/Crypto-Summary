# クラウドへの配備

アプリ (Crypto-Summary) をクラウドのコンテナサービスで動かし、PBR Lending の
クローラー (PBRLending-History-Check) は手元に残して、取得データをファイル同期で
運ぶ構成の手順。

> **起動までを順に追いたい場合は [`pbr-setup.md`](./pbr-setup.md) を参照。**
> 同一マシンで動かす場合と、クラウド＋手元に分ける場合の手順が構成別にまとまっている。
> こちらは配備先の選び方・環境変数・バックアップなど、その周辺を扱う。

## なぜクローラーを持っていかないか

技術的に動かないのではなく、設計上そもそも合わない。

- **クロールに人間の手が要る。** PBR Lending へのログインは手動で、
  「ログインして続行を押す」まで待つ実装になっている。無人実行できない。
- **noVNC は口座にログイン済みブラウザの全操作権限**を与える。手元では
  127.0.0.1 に閉じているが、クラウドでは公開せざるを得ず、守りはパスワード 1 枚になる。
- **ブラウザプロファイルに PBR Lending のセッション Cookie が残る。**
  これをクラウドに置くのは、貸出口座のセッションを他人のサーバーに預けるのと同じ。

クローラーは手元で動かし、`outputs` ディレクトリだけを同期すれば十分。
アプリ側はディレクトリを読むだけなので、同期の手段は問わない。

## 手元の Linux サーバーで試す

クラウドへ出す前に、同じ構成を手元の Linux サーバーで確かめられる。クローラーは
Windows 側、アプリは Linux 側という実運用と同じ形になるので、同じディレクトリを
送受信してしまう事故も起きない。

### ログインをどうするか

`DATA_DIR` の有無でモードが決まる。

| 設定 | モード | 向き |
|---|---|---|
| `DATA_DIR=/data` | マルチユーザー（Google ログイン） | 本番 |
| `DATA_DIR=`（空） | シングルユーザー（ログイン無し） | LAN でのお試し |

**LAN の http では Google ログインは使えない。** Google は localhost 以外の
リダイレクト URI に http を認めないため、`http://192.168.x.x:8000` を登録できない。
お試しはシングルユーザーで行う。その場合アプリは **LAN 上の誰でも開ける**ので、
信頼できるネットワークに限ること。

### 手順

リポジトリを Linux サーバーへ置き（git clone なり rsync なり）、`.env` を作る。

```bash
BASE_URL=http://192.168.1.50:8000        # サーバーの LAN アドレス
DATA_DIR=                                 # 空 = ログイン無し
SYNCTHING_API_KEY=<openssl rand -hex 24 で生成>
```

起動:

```bash
docker compose -f docker-compose.cloud.yml up -d --build
```

`http://192.168.1.50:8000` を開き、インポート画面の同期カードにある
「ファイル同期の相手を登録（Syncthing）」でこのサーバーのデバイス ID を確認する。
Windows 側のクローラー画面で同じ操作をして、どちらかに相手の ID を貼れば
もう片方に承認待ちが出る。

### 開けておくポート

| ポート | 用途 |
|---|---|
| 8000/tcp | アプリの画面 |
| 22000/tcp・22000/udp | Syncthing の同期 |
| 21027/udp | Syncthing のローカル探索（同一 LAN なら相手を自動で見つける） |

同一 LAN なら 21027 のおかげで相手を自動発見するので、外部リレーを経由しない。

### 既存の台帳を持っていく場合

シングルユーザーモードの DB は `/data/ledger.db`。手元の台帳を使いたいなら
ボリュームへコピーする。

```bash
docker compose -f docker-compose.cloud.yml cp <手元の.db> app:/data/ledger.db
docker compose -f docker-compose.cloud.yml restart app
```

空のまま始めて、同期で届いた PBR データが取り込まれるかを見るだけでも、
経路の確認としては十分。

## 配備先の選び方

台帳は SQLite (WAL) なので、**永続ブロックボリュームが付くサービス**を選ぶ。

| 種別 | 例 | 可否 |
|---|---|---|
| ブロックボリュームが付く | Fly.io / Render / Railway / 小さな VM | そのまま動く |
| ファイルシステムが揮発 | Cloud Run / App Runner | 不可（外部 DB への移行が必要） |
| ネットワークストレージ | EFS / Azure Files | 非推奨（SQLite のロックが不安定） |

**インスタンスは 1 台に固定する。** SQLite は複数プロセスからの同時書き込みを
前提にしていない。水平スケールさせない設定にすること。

## 環境変数

```bash
BASE_URL=https://cs.example.com        # 必須。カンマ区切りで複数可（下記「リバースプロキシ」参照）
CS_ROOT_PATH=                          # 任意。サブパス配信の接頭辞。通常は BASE_URL のパスから自動決定
DATA_DIR=/data                         # 必須。ボリュームのマウント先
GOOGLE_CLIENT_ID=...                   # ログインに必要
GOOGLE_CLIENT_SECRET=...
ADMIN_EMAILS=you@example.com
CS_SECRET_KEY=...                      # API キーの暗号化マスター鍵
PBR_CRAWL_DIR=/data/pbr-outputs        # ファイル同期の宛先
COINGECKO_API_KEY=                     # 任意
SECRET_KEY=                            # 任意（未設定なら自動生成して永続化）
```

Google Cloud Console 側で、`BASE_URL` に挙げた**各入口**の `/auth/callback` を
リダイレクト URI として登録しておくこと。

秘密情報 (`GOOGLE_CLIENT_SECRET` / `CS_SECRET_KEY`) は配備先のシークレット管理へ。
`.env` をイメージやリポジトリに含めないこと。

## 起動

```bash
docker compose -f docker-compose.cloud.yml up -d --build
```

ヘルスチェックは `GET /api/health`（認証不要、`{"status":"ok"}` を返す）。

## リバースプロキシの配下に置く（Nginx Proxy Manager 等）

サブドメイン（`https://cs.example.com`）でもサブパス
（`https://example.com/crypto/`）でも動く。TLS はプロキシ側で終端して構わない。

- 公開 URL を `BASE_URL` に書く。**カンマ区切りで複数書ける**ので、ループバックと
  公開 URL を並べておけば、設定を変えずにどちらの入口からもログインできる:

  ```bash
  BASE_URL=https://example.com/crypto,http://localhost:8000
  ```

- リダイレクト URI は「今開いている入口」から組み立てられる。`BASE_URL` に
  挙げた各入口の `/auth/callback` を Google に登録しておけばそれだけで足りる。
  一覧に無い Host で来たリクエストは先頭エントリへ倒す（Host ヘッダ詐称対策）。
- TLS 終端の内側ではリクエストが平文 http に見えるが、ホスト:ポートが一致する
  エントリが https で登録してあればそちらのスキームが使われる。
  登録 URL に既定ポート（`:443` / `:80`）は書かないこと（文字列で照合するため）。
- **サブパスで公開する場合は、プロキシで接頭辞を落とさずそのまま転送すること。**
  nginx なら `proxy_pass http://crypto-summary:8000;`（末尾スラッシュなし）。
  Nginx Proxy Manager なら Custom Location に `/crypto` を作り、Forward
  Hostname/IP とポートだけを書く（Forward 先にパスを書かない）。接頭辞を
  落とすと StaticFiles のマウントが一致せず、静的ファイルが 404 になる
  （Starlette 1.3 で実測）。Host ヘッダもそのまま転送すること（NPM は既定で転送）。
- 接頭辞は `BASE_URL` 先頭エントリのパス部分から自動で決まる。`CS_ROOT_PATH` で
  明示もできる（空は「自動」、`/` は「ルート配信を強制」）。
- 反映タイミング: `BASE_URL` の変更はリダイレクト URI には即時反映されるが、
  接頭辞（root_path）と Cookie の Secure は起動時に固定されるため**要再起動**。
- `BASE_URL` は 1 か所で管理する（env か初回セットアップ画面のどちらか）。
  env で渡していると、管理画面から変更しても再起動時に env の値へ戻る。
- http のエントリが 1 つでもあるとセッション Cookie の Secure は付かない
  （そのエントリでログインできなくなるため）。全入口を https にすれば付く。
- セッション Cookie 名は `cs_session`。同一ドメインのサブパスに
  Asset Summary（`session`…既定名）と並べても取り合いにならない。

## PBR データのファイル同期

クラウドに置いたアプリからクローラーを操作することはない。クロールは手元の機械で
行い、その結果だけをファイル同期で届ける。同期の手段は問わない（Syncthing /
rsync / rclone など）。

| | 場所 | 役割 |
|---|---|---|
| 送信側 | 手元の `<PBRLending-History-Check>/outputs/` | クロールと手動インポートの出力 |
| 受信側 | クラウドの `<データボリューム>/pbr-outputs/` | `PBR_CRAWL_DIR` が指す先 |

同期するファイルは 4 つだけ。

| ファイル | 役割 |
|---|---|
| `pbrlending_crawled.latest.json` | クロール結果（当年分） |
| `last_crawl.json` | クロールの成否（無いと既定では取り込まない） |
| `viewer_transfers.json` | クローラー画面へ手動インポートした入出金 |
| `viewer_ledger.json` | 同上（日次レポート） |

`captures/` は同期しない。生のスクレイピング結果で容量が大きく、取り込みには
使わない。

### 画面から相手を登録する（Syncthing）

Syncthing を使う場合、GUI を触らずにアプリの画面から相手を登録できる。
`SYNCTHING_URL` と `SYNCTHING_API_KEY` を設定すると、インポート画面の同期カードに
「ファイル同期の相手を登録」が出る（サーバー全体の設定なので管理者のみ）。

1. 片側の画面で相手のデバイス ID を貼り付けて「登録」
2. もう片側の画面に「承認待ち」として出るので「承認」を 1 回押す
3. 接続が成立して同期が始まる

フォルダのパス・種別（送信のみ／受信のみ）・除外設定は、それぞれの側の
アプリが自動で正しく設定する。手順と API の詳細は
[`syncthing-pairing.md`](./syncthing-pairing.md) を参照。

`docker-compose.cloud.yml` には同じボリュームを見る Syncthing サイドカーを
入れてある。`SYNCTHING_API_KEY` を `.env` で渡すこと（このキーは Syncthing
全体を操作できるので、手元の個人 Syncthing のものは使わず、サイドカー専用に
生成する）。同期の待受は 22000/tcp・22000/udp。GUI(8384) は公開しない。

### 送信側（手元）の設定

画面から登録しない場合、または手動で確認したい場合。Syncthing の GUI では:

1. `<PBRLending-History-Check>/outputs` をフォルダとして追加する
2. フォルダ種別を **「送信のみ」** にする（アプリ側は読むだけなので、
   受信側の変更が手元へ戻ってこないようにする）
3. 除外設定 (`.stignore`) に次を入れて、必要なファイルだけを送る

```
// 取り込みに使う 4 ファイル以外は送らない
!pbrlending_crawled.latest.json
!last_crawl.json
!viewer_transfers.json
!viewer_ledger.json
*
```

年ごとの CSV (`pbrlending_2026_*.csv`) も送りたい場合は、`!` 行に足す。
取り込みには使わないが、手元のバックアップ目的なら有用。

### 受信側（クラウド）の設定

同期先をデータボリューム内の `pbr-outputs` にして、フォルダ種別を
**「受信のみ」** にする。`PBR_CRAWL_DIR=/data/pbr-outputs` と揃える。

コンテナ内へ直接同期できない配備先（Fly.io / Render など）では、
同期クライアントをサイドカーとして同じボリュームに載せるか、ホスト側の
ボリューム実体へ同期する。ボリュームの実体に触れない配備先では、
rclone などでオブジェクトストレージ経由にするか、手元から
`docker cp` / `fly ssh sftp` 相当で置く。

### 到着の確認

インポート画面の同期カードにある「取り込み元ファイル」を開くと、
同期先のパスと、4 ファイルそれぞれの最終更新・サイズ・未着かどうかが出る。
届いていないファイルは「未着」と表示される。

### 動作

**片方向で十分。** アプリはこのディレクトリを読むだけで、書き込まない。

**ファイルが順に届くことへの対応は入っている。** 取り込み元ファイルの更新から
30 秒間は自動取り込みを見送る（`SETTLE_SECONDS`）。片方だけ新しい状態や
書き込み途中を読まないため。画面の同期ボタンと CLI はこの待ちを無視する。

同期が届くと、次にアプリの画面を開いたときに自動で取り込まれる。取り込みの
判定は「取り込み元ファイルの更新時刻とサイズ」の指紋で行うので、クロールして
いなくても、手動インポートしたファイルが届いただけで反映される。

### クローラー操作のタブについて

`PBR_VIEWER_URL` を書かなければ、サイドバーの「PBR クローラー」タブは出ない。
クラウド構成では既定でこの状態（`docker-compose.cloud.yml` は空のまま渡す）。

手元運用でタブを使いたい場合だけ URL を設定する。なお https で公開している
アプリから `http://` のビューアを iframe に出すことはできない（mixed content）。

**連携の表示は利用者ごとの設定。** `PBR_CRAWL_DIR` を設定してもそれだけでは
UI に出ず、各利用者がインポート画面の「集計の設定」でオンにしたときに出る。
全員が PBR Lending の口座を持つとは限らず、口座があっても年次の公式 CSV を
取り込むだけならクローラーは要らないため（マルチユーザーで効いてくる）。
クローラー連携を使ったことがある利用者は、設定しなくても有効になる。

## バックアップ

`/data` ボリュームだけ取ればよい。中身は台帳 (`*.db`)、口座グループ・表示設定・
暗号化された API キー (`*.json`)、セッション鍵 (`_session_key`)、
同期記録 (`*.pbr_sync.json`)、および同期されてきた `pbr-outputs/`。

`CS_SECRET_KEY` を失うと登録済み API キーを復号できなくなる。ボリュームとは
別に控えておくこと。

## 手元に残すもの

- クローラー本体（Docker でもホストでも）
- クロールの実行と、公式 CSV の手動インポート
- `outputs` を同期する仕組み

アプリのクローラータブ (`PBR_VIEWER_URL`) は利用者のブラウザから解決されるので、
手元のビューアを指したままでよい。ただしアプリを https で公開している場合、
`http://` のビューアは mixed content でブロックされ iframe には表示されない
（「新しいタブで開く」は使える）。
